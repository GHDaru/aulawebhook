Casos de Uso

Aula introdutória · Requisitos Funcionais na perspectiva do usuário

O que é um Caso de Uso?
Capturando o que o sistema deve fazer — do ponto de vista de quem o usa.

Definição

Um Caso de Uso descreve uma sequência de interações entre um ator e o sistema, com o objetivo de alcançar um resultado de valor para o ator.

Introduzido por Ivar Jacobson em 1987 (Ericsson) e popularizado com a UML nos anos 1990. Hoje é parte do Unified Process e do RUP.

🧠 Metáfora do Caixa Eletrônico

Pense num caixa eletrônico: você não se importa com os circuitos internos — você quer sacar dinheiro. O Caso de Uso captura exatamente essa intenção: o que o usuário quer realizar, sem entrar em como o sistema faz isso por dentro.

Exemplos do dia a dia mapeados como Casos de Uso

🛒 E-commerce: Realizar Compra · Rastrear Pedido · Cancelar Pedido · Aplicar Cupom de Desconto
🏦 App Bancário: Transferir via PIX · Emitir Boleto · Consultar Extrato · Bloquear Cartão
📚 Sistema Acadêmico (UDESC): Matricular em Disciplina · Lançar Notas · Emitir Histórico · Solicitar Trancamento
🏥 Clínica Médica: Agendar Consulta · Emitir Receita · Registrar Prontuário · Realizar Check-in
🚗 Aplicativo de Transporte: Solicitar Corrida · Avaliar Motorista · Cadastrar Forma de Pagamento

✅ Caso de Uso (correto)

  • Realizar Login
  • Emitir Nota Fiscal
  • Agendar Entrega
  • Recuperar Senha

❌ Não são Casos de Uso

  • Clicar no botão "Enviar"
  • Banco de dados de clientes
  • Algoritmo de hash de senha
  • Tela de login com campos X e Y

⚠️ Caso de Uso ≠ Funcionalidade técnica

Um caso de uso é sempre expresso do ponto de vista do objetivo do usuário. "Criptografar senha com bcrypt" não é um caso de uso — é um detalhe de implementação. "Cadastrar nova senha" sim.

Atores e Sistema
Quem interage com o sistema — e o que o sistema representa.

O que é um Ator?

Um ator é qualquer entidade externa ao sistema que interage com ele. Pode ser uma pessoa, outro sistema, ou até um evento de tempo.

🧠 Metáfora do Palco

O sistema é o palco. Os atores estão na plateia — eles enviam comandos para o palco e recebem respostas, mas nunca entram nele. Tudo que acontece dentro do palco é responsabilidade do sistema.

Tipos de Atores com exemplos

👤 Ator Humano

Papel, não pessoa específica.

  • Cliente no e-commerce
  • Aluno no sistema acadêmico
  • Professor no portal UDESC
  • Administrador no ERP
  • Caixa no supermercado

🤖 Ator Sistema Externo

Outro software que usa ou alimenta o sistema.

  • Gateway de Pagamento no checkout
  • API do Correios no frete
  • SIGA/UDESC enviando dados
  • Sistema de NF-e na nota fiscal

⏰ Ator Temporal

O tempo como gatilho de ações.

  • Agendador gerando relatório diário
  • Timer expirando sessão inativa
  • Cron enviando e-mail mensal

🎭 Ator Principal vs. Secundário

  • Principal: inicia o caso de uso. Ex.: Cliente clica "Comprar"
  • Secundário: apoia ou é notificado. Ex.: Transportadora recebe pedido

O Sistema como "caixa preta"

📦 O princípio da Caixa Preta

No modelo de casos de uso, o sistema é uma caixa preta. Sabemos o que entra e o que sai, mas o caso de uso não descreve como o sistema processa internamente.

Errado: "O sistema consulta a tabela CLIENTES no banco Oracle e retorna os dados."
Certo: "O sistema exibe os dados do cliente."

Estrutura de um Caso de Uso
Como escrever um caso de uso completo — do nome às exceções.

Elementos obrigatórios

  • Nome — verbo + substantivo
  • Ator principal
  • Pré-condições
  • Fluxo principal
  • Fluxos alternativos
  • Fluxos de exceção
  • Pós-condições (sucesso)
  • Pós-condições (falha)

🧠 Metáfora da Receita de Bolo

Um caso de uso é como uma receita: tem ingredientes necessários (pré-condições), passo a passo (fluxo principal), variações (fluxo alternativo), e o que fazer se der errado (fluxo de exceção). O resultado final é o bolo pronto (pós-condição).

Exemplo completo: Realizar Login

UC-01 · Realizar Login
Ator principalUsuário (Aluno ou Professor)
Pré-condiçõesUsuário possui cadastro ativo no sistema. Usuário não está autenticado.
Fluxo principal1. Usuário acessa a página de login
2. Usuário informa e-mail e senha
3. Usuário clica em "Entrar"
4. Sistema valida as credenciais
5. Sistema redireciona para a página inicial
6. Sistema exibe mensagem de boas-vindas
Fluxo alternativo APrimeiro acesso:
4a. Sistema detecta que é o primeiro login
4b. Sistema solicita troca obrigatória de senha
4c. Usuário define nova senha → retorna ao passo 4
Fluxo de exceção E1Credenciais inválidas:
4e. Sistema exibe "E-mail ou senha incorretos"
4f. Após 3 tentativas, conta é bloqueada por 15 min
Pós-cond. sucessoUsuário autenticado, sessão iniciada, log de acesso registrado.
Pós-cond. falhaUsuário não autenticado, tentativas incrementadas.

Mais exemplos de casos de uso descritos

UC-02 · Realizar Compra (E-commerce)

AtorCliente
Pré-cond.Cliente logado, ao menos 1 item no carrinho.
Fluxo principal1. Cliente acessa o carrinho → 2. Confirma itens → 3. Informa endereço de entrega → 4. Escolhe forma de pagamento → 5. Sistema processa pagamento via Gateway → 6. Sistema gera nº do pedido → 7. Cliente recebe confirmação por e-mail
Fluxo alt. APagamento recusado: sistema notifica cliente, mantém carrinho.
Pós-cond.Pedido criado, estoque decrementado, e-mail enviado.

UC-03 · Emitir Histórico Escolar (UDESC)

AtorAluno
Pré-cond.Aluno autenticado, sem pendências financeiras.
Fluxo principal1. Aluno acessa "Documentos" → 2. Seleciona "Histórico Escolar" → 3. Escolhe idioma (PT/EN) → 4. Sistema gera PDF com assinatura digital → 5. Aluno faz download
Fluxo alt. APendência financeira: sistema bloqueia emissão e exibe débitos.
Pós-cond.PDF gerado, solicitação registrada no log.

🧠 Dica do nome do Caso de Uso

Sempre use Verbo no infinitivo + Substantivo: Realizar Pagamento, Emitir Nota Fiscal, Cancelar Pedido. Evite nomes vagos como "Dados do Usuário" ou "Processamento".

Diagrama de Casos de Uso (UML)
Representação visual dos casos de uso, atores e relacionamentos.

Notação UML básica

  • Boneco palito → Ator
  • Elipse → Caso de Uso
  • Retângulo → Fronteira do sistema
  • Linha sólida → Associação ator–UC
  • <<include>> → UC sempre inclui outro
  • <<extend>> → UC opcionalmente estende outro
  • Seta vazia → Generalização de ator

Diagrama Interativo — Sistema de E-commerce

Relacionamentos em detalhe

<<include>>

Sempre acontece. O UC base obrigatoriamente executa o UC incluído.

  • Realizar Compra inclui Autenticar Usuário
  • Emitir Nota Fiscal inclui Validar CNPJ
  • Transferir PIX inclui Verificar Saldo

<<extend>>

Opcional/condicional. O UC estendido é executado apenas em certas condições.

  • Realizar Compra é estendido por Aplicar Cupom
  • Agendar Consulta é estendido por Notificar Médico
  • Realizar Login é estendido por Ativar 2FA

🧠 Include vs. Extend — a metáfora do aeroporto

Include é como o check-in: toda viagem sempre passa pelo check-in. Extend é como a sala VIP: só quem tem acesso especial (condição) entra nela. O voo acontece com ou sem a sala VIP.

Generalização de Ator

Exemplo: No sistema acadêmico, Usuário é o ator genérico. Aluno e Professor herdam de Usuário — ambos podem "Realizar Login", mas só o Professor pode "Lançar Notas" e só o Aluno pode "Solicitar Matrícula".

Boas Práticas e Erros Comuns
O que separa um bom caso de uso de um caso de uso problemático.

✅ Boas Práticas

  • Nome: Verbo + Substantivo no infinitivo
  • Perspectiva sempre do ator, nunca do sistema
  • Granularidade média: um objetivo por UC
  • Cobrir fluxos alternativos e de exceção
  • Usar linguagem de negócio, não técnica
  • Validar com stakeholders (não só com devs)

❌ Erros Comuns

  • UCs orientados à interface (clicar, digitar)
  • UCs muito granulares: "Validar campo CPF"
  • UCs muito amplos: "Gerenciar Sistema"
  • Misturar design e requisito
  • Esquecer fluxos de exceção
  • Ator = pessoa física (João da Silva) em vez de papel

Erros com exemplos práticos

🚫 Erro 1: UC orientado à interface

Errado: "Clicar no botão Salvar" · "Preencher campo E-mail" · "Selecionar dropdown de Estado"
Certo: "Cadastrar Endereço de Entrega" — o caso de uso é o objetivo, não o gesto.

🚫 Erro 2: Granularidade inadequada

Muito pequeno: "Validar CPF", "Gerar Token JWT", "Hash de Senha" — esses são passos internos, não casos de uso.
Muito grande: "Gerenciar Usuários" — quebre em UCs específicos.
Certo: "Cadastrar Usuário", "Alterar Senha", "Desativar Conta".

🚫 Erro 3: Ator = pessoa física

Errado: Ator "João — Gerente Financeiro da Empresa X"
Certo: Ator "Gerente Financeiro" — representa o papel, não o indivíduo.

Quando usar (e quando não usar) Casos de Uso

✅ Use Casos de Uso quando:

  • O sistema tem múltiplos perfis de usuário
  • Os requisitos são orientados a processos de negócio
  • O projeto usa UP, RUP ou análise orientada a objetos
  • Precisa comunicar requisitos com stakeholders não técnicos
  • O sistema tem fluxos complexos com muitas variações

⚠️ Cuidado ou evite quando:

  • Time ágil puro com sprints curtos (prefira User Stories)
  • Sistema muito simples, poucos fluxos
  • API pura sem interface de usuário visível
  • Equipe pequena onde o custo de manutenção é alto

🧠 Metáfora do Mapa

Casos de Uso são como mapas: não mostram todos os detalhes da cidade (código, banco de dados), mas dão a visão geral do território (o que o sistema faz). Antes de construir a cidade, você precisa do mapa.
